## 1. Перегляд Business Case Влада

Колега запропонував рішення для:

**Quality Control Automated Vision System** — система автоматизованого візуального контролю якості у виробництві.

### Основний акцент:

- зниження людських помилок,
- зменшення гарантійних витрат,
- 100% інспекція в реальному часі,
- застосування AI/Computer Vision.

### Business case написаний чітко, містить:

- проблему (manual inspection, 2% error rate),
- ціль (95% пом'якшення помилок),
- фінансовий ефект ($1.5M savings),
- обмеження (PES integration, industrial hardware),
- ключові бізнес-результати.

## 4. Аналіз технічного рішення

Влад запропонував архітектуру:

- Modular edge-based system
- AI Service (Python + TensorRT)
- Camera Controller (C++ + Qt)
- ADDS Controller
- ZMQ for communication
- PostgreSQL for storage
- Integration via REST
- UI in Qt

### Позитивні моменти

| № | Перевага | Чому це добре |
|---|----------|---------------|
| 1 | Edge-based computing | Мінімізація latency, відсутність залежності від cloud |
| 2 | TensorRT + CUDA | Найкращий варіант для real-time CV |
| 3 | ZMQ messaging | Легка вага, low latency |
| 4 | Сервісна сегментація | Хороша maintainability |
| 5 | C++ для camera pipeline | Максимальна продуктивність |
| 6 | Self-calibration module | Унікальна та дуже цінна частина дизайну |

### Проблемні моменти

| № | Недолік | Пояснення |
|---|---------|-----------|
| 1 | Немає redundancy | Якщо GPU падає — вся лінія зупиняється |
| 2 | Без шифрування | Безопасність під питанням |
| 3 | Python AI Service може стати bottleneck | Особливо при batch >1 |
| 4 | Немає описаної стратегії retraining pipeline | А це критично |
| 5 | PostgreSQL на edge може стати single point of failure | Ризики втрати даних |

**T2 — TensorRT optimization vs Accuracy**

- підвищує FPS
- можливе падіння точності при INT8 quantization
- → Впливає на QA-3, CT-1, UC-3

#### Risks (R)

**R1 — Accuracy degradation**

- → AD-2, AD-5, CT-1, QA-3

**R2 — Hardware failures (GPU, cameras)**

- → AD-1, AD-3, CN-2

**R3 — Pipeline may exceed 1s limit**

- → QA-1, CN-1, UC-3

**R4 — PES API latency or unavailability**

- → QA-6, UC-2, CN-3

#### Sensitivity Points (S)

**S1 — Inference time**

- 1ms збільшення в AI → впливає на весь pipeline
- → AD-2, QA-1, CN-1

**S2 — Calibration drift**

- → AD-3, CT-1, UC-4

#### Non-Risks (N)

**N1 — Usability UI not affecting core system**

**N2 — Industrial constraints fully covered by hardware choice**

## Загальний висновок

У межах виконання лабораторної роботи було проведено комплексну архітектурну оцінку рішення Влада, яке передбачає створення автоматизованої системи контролю якості на виробничій лінії (ADDS). Аналіз охопив бізнес-кейс, бізнес-драйвери, функціональні можливості, нефункціональні вимоги, архітектурні рішення, технічні обмеження, а також включав детальний tradeoff-аналіз згідно з методологією ATAM.

Насамперед було відзначено, що бізнес-кейс сформульований якісно та містить чітко визначені проблеми, бізнес-цілі й очікувані вигоди, зокрема зменшення помилок інспекції на 95% та значне скорочення гарантійних витрат. Порівняння бізнес-драйверів мого та Влада показало високу узгодженість у ключових пріоритетах: реальний час роботи, точність AI-моделі, інтеграція з Production Execution System (PES), безперервність роботи та усунення людського фактора. Водночас фінансовий аспект у колеги був менш акцентований, хоча він є одним із ключових мотиваторів для бізнесу.

Аналіз функціональних можливостей рішення показав їх відповідність бізнес-драйверам, а нефункціональні вимоги (QA-сценарії) були добре визначені та структуровані, що забезпечує можливість вимірювання якості системи. Зокрема, вимоги до продуктивності (≤1 сек аналізу), точності (≥99.85%), надійності (24/7 робота) та інтеграції (≤2 сек реакції від PES) чітко окреслюють межі прийнятності системи. Однак деякі аспекти, такі як вимоги до UX або метричні критерії підтримуваності, потребують уточнення.

Оцінка технічного рішення виявила низку сильних сторін: використання C++ для керування камерами забезпечує високу продуктивність, TensorRT і CUDA гарантують ефективне прискорення inference, ZeroMQ надає малу латентність у комунікації між сервісами, а розподілена модульна архітектура підвищує масштабованість і підтримуваність. Разом із тим виявлено низку потенційних проблем, включно з відсутністю redundancy для GPU, можливими затримками у PES API, питаннями безпеки у разі використання нешифрованого ZMQ, а також ризиком деградації точності моделі зі зміною виробничих умов.

Проведений tradeoff-аналіз дав змогу виявити точки чутливості (sensitivity points), зокрема залежність продуктивності від швидкості inference та залежність точності від умов калібрування. Також були визначені критичні tradeoffs, наприклад між продуктивністю та maintainability (C++ vs Python), або між оптимізацією моделі та можливим зниженням точності (INT8 quantization). Ризики, що були ідентифіковані, включають перевищення ліміту часу обробки, деградацію моделі, збої обладнання та нестабільність API виробничої системи.

Узагальнюючи, можна стверджувати, що рішення є технічно грамотним, добре узгодженим із бізнес-цілями та містить більшість необхідних компонентів для створення надійної системи автоматичного візуального контролю. Водночас робота виявила критичні архітектурні аспекти, які потребують додаткової уваги: забезпечення відмовостійкості, захист комунікацій, управління життєвим циклом AI-моделі та точніша регламентація вимог до продуктивності. Подальша робота над цими аспектами суттєво підвищить зрілість архітектури та її готовність до реального промислового впровадження.
